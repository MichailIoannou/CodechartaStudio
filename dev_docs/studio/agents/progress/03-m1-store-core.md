### 1. Paths and ids
- Newtypes `ProjectId`, `FolderId`, `SnapshotId` live in a new `codecharta-core-api/src/ids.rs` (shared by
  the later `projects` and `snapshots` types), generated by one `store_id!` macro: `try_from`/`into`
  `String`, `^[a-z0-9-]{1,96}$`, `as_str`, `Display`. The other newtypes of section 3 (`CommitHash`,
  `FullCommit`, `PickToken`, `Label`, `ProjectName`, `Description`) arrive with their first user (M2/M3).
  None of them is in the TypeScript contract yet, because no method names them.
- `ids.rs` (core): `new_project_id`, `new_folder_id` from `getrandom::fill` (8 bytes, hex). `getrandom`
  0.4.3 was already in `Cargo.lock` through `tempfile`, so no new package. `new_token` and
  `imported_snapshot_id` arrive with M2/M3.
- `store/paths.rs`: `StorePaths` (`store_file`, `session_file`, `lock_file`, `projects_dir`, `project_dir`,
  `project_file`, `folder_snapshots_dir`, `snapshot_dir`, `map_file`), file-name constants and
  `STAGING_FOLDER_PREFIX`. The inside-root check is lexical (the path must be the root plus only normal
  components), which is what an id-built path can get wrong; it does not canonicalise, since most of these
  paths do not exist yet. `confine_to_folder` refuses empty, absolute and `..` paths (`BAD_REQUEST`), a
  missing file is `NOT_FOUND`, a canonical path outside the canonical folder is `NOT_ALLOWED`. The
  symlink test is `cfg(unix)`; no `dunce`: both sides are canonicalised the same way, so a `\\?\` prefix
  on Windows is on both (not verified on Windows).

### 2. Atomic writes
- `store/atomic.rs`: `read_json`, `read_json_if_exists` (missing file is `None`; bad JSON is `IO` with
  `InvalidData`), `write_json_atomic` (pretty JSON + newline, temporary file `.tmp-<random>` in the same
  folder via `tempfile::Builder`, `sync_all`, rename with retries, then `TempPath::keep`; the temporary file
  is removed when anything fails), `ProjectLocks` (`lock(&ProjectId) -> OwnedMutexGuard`, tokio mutex per
  project so a guard may be held across an `await` in M2).
- Retry: 5 retries after the first attempt, 20 ms doubling (named constants). Transient = `PermissionDenied`,
  plus raw OS errors 32/33 (sharing/lock violation) on Windows only. The retry test injects the failure
  through a private `write_json_atomic_with(path, value, rename)` seam; the real Windows failure is not
  reproducible on Linux (03-M0 item 3.3) and stays unverified. Extra tests: `should_give_up_after_the_last_retry`,
  `should_replace_the_file_with_the_new_content`, `should_answer_none_for_a_missing_file_and_io_for_bad_json`.

### 3. Open, migrations, sweep
- New error code `STORE_NEWER_SCHEMA` (appended: `ErrorCode` variant, `ErrorCode::ALL` now 14,
  `CoreError::StoreNewerSchema { found, supported }` and its `code()` arm); contract regenerated
  (`ErrorCode.ts`, `CORE_ERROR_CODES`). The export-contract test `should_list_every_error_code` asserted
  that `INTERNAL` is the last code, which breaks on every append; it now checks the whole list in
  `ErrorCode::ALL` order instead.
- `store/mod.rs`: `Store::open(root)` creates the root, reads `schemaVersion` from the raw JSON (so a newer
  file whose other fields changed is still reported as newer), creates `store.json`
  (`{ schemaVersion, createdAt }`, RFC 3339 UTC via `humantime`) when missing, fails with
  `STORE_NEWER_SCHEMA` before touching anything, sweeps, then runs `MIGRATIONS` whose `to_version` is
  above the stored version, in list order, rewriting only `schemaVersion` in `store.json` after each. A
  `store.json` without a numeric `schemaVersion` (or invalid JSON) is `IO` and is left untouched. A test
  keeps `MIGRATIONS` ascending and ending at `STORE_SCHEMA_VERSION`. The migration-order test uses a
  private `open_with_schema` with its own list.
- **Deviation:** the sweep is in `store/sweep.rs`, not `store/mod.rs`. It only looks in the store's own
  places — `.tmp-*` files in the root, in `projects/<projectId>/` and in each snapshot folder, and
  `.incoming-*` folders in `projects/<projectId>/snapshots/<folderId>/` — and only below names that parse
  as ids, so nothing a user put into a chosen store folder is deleted. Symbolic links are not followed.
  `StorePaths::project_snapshots_dir` was added for it.
- `Store` also owns the `ProjectLocks` (`project_locks()`), for M2.

### 4. Lock
- New error code `STORE_LOCKED` (appended; `ErrorCode::ALL` now 15; `CoreError::StoreLocked { store_root }`).
  `CONFLICT` was not reused: the plan, `StoreProblemCode` and the UI need to tell this case apart.
- `store/lock.rs`: `StoreLock::acquire(root)` creates the root, opens `.lock` (create, write, no truncate)
  and calls std `File::try_lock`; `WouldBlock` is `STORE_LOCKED`, anything else `IO`. The `File` is the
  guard; dropping it (or the process ending) releases the lock. No `fs4`.
- `Store::open` takes the lock first, before `store.json` is read or created; `Store::open_read_only(root)`
  takes no lock and writes nothing: it only checks `schemaVersion` when `store.json` exists (newer is
  `STORE_NEWER_SCHEMA`, older than current is `CONFLICT` "needs an upgrade; open it in the app once", which
  cannot happen while `MIGRATIONS` is empty). `Store::is_writable()` tells the two apart.
- Two-process tests in `codecharta-core/tests/store_lock.rs`: the second process is `cc-fake-tool
  hold-store-lock <root>` (new mode: takes `StoreLock`, prints `locked`, holds until stdin closes).
  Linux uses `flock`; Windows (`LockFileEx`) is not verified here.

### 5. Session
- `store/session.rs`: `SessionRepository<'store>` (from `Store::session()`) with `active_project() ->
  CoreResult<Option<ProjectId>>` and `set_active_project(Option<&ProjectId>)`; `session.json` is
  `{ "activeProjectId": "p-..." | null }`, written atomically. A missing file is no active project; an
  unreadable one (bad JSON or an invalid id) is logged and also reads as none, so a damaged file never
  blocks start-up. Writes need a writable store (`Store::ensure_writable`, `NOT_ALLOWED` otherwise).
- Not here: checking that the project exists (`projects.setActive` in M2 must do it, and clear a stale id
  when a project is deleted), and the RPC methods `projects.getActive` / `projects.setActive` (M2).

### 6. store.status and degraded serve
- Api: `methods/store.rs` with `StoreProblemCode { StoreLocked, StoreNewerSchema, Io }` (wire
  `STORE_LOCKED`, `STORE_NEWER_SCHEMA`, `IO`; **the plan's `IoError` is `Io`**, matching plan 01's `IO` code),
  `StoreStatus { problem }` and `store.status` (renderer, `EmptyParams`). Contract regenerated
  (`StoreProblemCode.ts`, `StoreStatus.ts`, `coreApi.ts`, `store.status` in the renderer allow-list).
- Core: `store/state.rs` `StoreState::{Open(Store), Unavailable(CoreError)}`; `Core` holds it in a
  `OnceLock`. `Core::open` still creates nothing; `Core::open_store()` opens the store for writing once
  (only `serve` calls it, so `doctor` never locks or creates a store); `Core::store() -> CoreResult<&Store>`
  answers the start-up error again on every call (`STORE_LOCKED`, `STORE_NEWER_SCHEMA`, `IO` with the same
  context; anything else `INTERNAL`) — **this is the hook every store method of M2/M3 must go through**;
  `Core::store_status()`. A store that was never opened is `INTERNAL`.
- `serve` logs the problem as a warning and keeps serving; `paths.*`, `tools.*`, `core.*` are unaffected.
  The lock is released when the `Core` is dropped at the end of `serve` or the process ends. A store root
  changed through `paths.setStoreRoot` takes effect on the next start (the shell relaunches; M6).
- Protocol tests (`codecharta-cored/tests/protocol.rs`): the two of the plan plus
  `should_report_store_locked_while_another_process_holds_the_store`; the healthy test also checks that
  `store.json` and `.lock` exist and that a second writer gets `STORE_LOCKED` while `serve` runs.
  `ServingCore::launch(data_dir, configure)` / `started_and_greeted_in(data_dir)` let a test prepare the
  data folder first.
- Acceptance "starting the app creates store.json and .lock": checked through
  `codecharta-core --data-dir <tmp> serve` over stdio (hello, `store.status` → `{"problem":null}`, then
  `<tmp>/store` held `.lock` and `store.json` `{ "schemaVersion": 1, "createdAt": "…Z" }`), not through the
  app: the Electron shell (01-M3) is not on this branch. Not checked on Windows / `%APPDATA%`.
- Plan 03 text corrected in this commit: "Required from plan 01" (store root and data-dir names), the
  module table (`store/mod.rs`, new `store/state.rs`), the error/`StoreProblemCode` block, the crate list.
